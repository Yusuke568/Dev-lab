# SES勤怠管理・勤務報告書システム要件定義書
## 03. 非機能要件定義書

### 3.1 性能・スケーラビリティ要件

#### 3.1.1 応答性能 (Response Time)
| 処理分類 | 目標値 | 測定条件・備考 |
| :--- | :--- | :--- |
| **画面初期表示** | 1.5秒以内 | 社員一覧、SES勤怠月次カレンダー表示 |
| **勤怠非同期保存 (API)** | 0.5秒以内 | `SesAttendanceApiAction` への1日分更新・計算結果返却 |
| **月間テンプレート適用** | 1.0秒以内 | 1ヶ月分（28〜31日）の一括初期化処理 |
| **有給一括付与処理** | 2.0秒以内 | 全社員対象のトランザクションバッチ処理 |

#### 3.1.2 同時実行性・スループット
- **想定同時アクセス数**: 通常時 50〜100セッション、月末締め日ピーク時 300セッション。
- **コネクションプール**: Tomcat `META-INF/context.xml` にて最大100コネクション（`maxTotal="100"`, `maxIdle="30"`）を設定し、枯渇を防止。

## 3.2 アーキテクチャ・保守性・品質要件

#### 3.2.1 クリーンアーキテクチャ・ヘキサゴナル原則
1. **依存性の単方向徹底**:
   - `domain`（ビジネスルール）はフレームワーク（Servlet/JSP）や永続化（JDBC/SQL）に一切依存しない純粋なPOJOとする。
   - `usecase` は `domain` のインターフェース（Repository）を通じて操作し、具象クラス（`infrastructure`）に依存しない（依存性逆転の原則 DIP）。
2. **Fat Controller / Fat Service の排除**:
   - Controllerはリクエストの検証とルーティングのみを担当。
   - 計算・判定ロジックは必ずドメインエンティティまたはドメインサービス（`SettlementService`, `Article36ComplianceService` 等）に配置。

#### 3.2.2 テスト品質要件
- **ドメイン単体テスト (JUnit 5)**:
  - 複雑な計算（SES精算幅計算、36協定判定、中抜け休憩控除など）は、DB接続やWebコンテキストなしでミリ秒単位で実行可能な単体テストを整備。
  - テストカバレッジ基準: ドメイン主要ロジック 80%以上。

## 3.3 セキュリティ要件

#### 3.3.1 認証および認可 (Authentication & Authorization)
- **認証**:
  - `login_table` による社員ID・パスワード検証。
  - `HttpSession` によるログイン状態保持。
- **ロール別アクセス制御 (RBAC)**:
  - `UserRole.USER`: 自身の勤怠・週報のみ編集可能。
  - `UserRole.MANAGER`: 所属配下の閲覧・レビュー可能。
  - `UserRole.ADMIN`: 社員CRUD、有給付与、全社データの管理権限。
- **セッション管理**:
  - 無操作30分でセッションタイムアウト。
  - ログアウト時にセッションを明示的に破棄（`session.invalidate()`）。

#### 3.3.2 脆弱性対策
- **SQLインジェクション対策**:
  - すべてのDBアクセスに `PreparedStatement` を使用し、動的プレースホルダー（`?`）によるパラメータバインドを徹底。SQLファイルの直接文字列連結は禁止。
- **XSS（クロスサイトスクリプティング）対策**:
  - JSPでの表示にはスクリプトレットを廃止し、JSTL `<c:out>` またはEL式 `${...}` を使用してエスケープを自動適用。
- **CSRF対策 / 多重送信防止**:
  - 更新系処理はPOSTリクエストに限定。

## 3.4 データベース・永続化要件

#### 3.4.1 DBMSおよび文字コード
- **DBMS**: MySQL 8.0以上
- **ストレージエンジン**: InnoDB（ACIDトランザクション保証、外部キー制約対応）
- **文字セット**: `utf8mb4`（照合順序: `utf8mb4_general_ci`）- 絵文字・人名外字対応

#### 3.4.2 トランザクション管理
- `infrastructure.db.TransactionManager` による明示的な境界制御。
- 複数テーブルの更新（例: 社員登録＋ログインテーブル作成、有給一括付与）は単一トランザクション内で実行し、例外発生時は完全ロールバック。
