10. アーキテクチャ設計思想と開発の考え方
〜「自己防衛するドメイン」と4層の厳格な境界線〜

👉 MVCからの思考転換・概念対比は「09. MVCからの設計転換ガイド」をご覧ください

本プロジェクト（webapp2）は、Spring Boot等の重量級フレームワークに依存せず、純粋なJavaとServlet/JSP環境下で 「クリーンアーキテクチャ（Clean Architecture / Hexagonal）」の原則を徹底して実装しています。
なぜこの設計思想を採用しているのか、何を守らなければならないのかを解説します。

Chapter 01

コアメッセージ：DBやフレームワークは「カセット」にすぎない

ヘキサゴナル／クリーンアーキテクチャの真髄は「ゲーム機本体とカセット」の関係です。
ゲーム機本体（ドメイン）は、差し込まれるカセット（MySQL、PostgreSQL、あるいはWeb UI、CLI）が何であるかを知りません。 端子（Interface）のルールさえ守られていれば、いつでも外部の都合を差し替えられます。

❌ 従来のアンチパターン（DB・画面中心）
  • DBのテーブル構造がドメインロジックを規定してしまう
  • TomcatやMySQLが動いていないと単体テストが一切できない
  • Beanはただの箱（getter/setter）で、不正な値でも自由に代入可能
⭕ 本プロジェクトの設計思想（ビジネスルール中心）
  • ドメイン層は標準Javaのみ。ServletもJDBCも知らない（外部依存ゼロ）
  • DB起動不要で、全テスト（20件）が0.8秒で完了する
  • オブジェクト自身が不正な状態を拒絶する（自己防衛モデル）
Chapter 02

4層クリーンアーキテクチャの責務と境界線

┌────────────────────────────────────────────────────────────────────────┐
│  controller 層 (Web / UI)                                              │
│  - FrontController, Action, ApiAction, View, JSP, CSS                 │
│  - 責務: HTTPリクエスト解釈、パラメータ検証、レスポンス返却(HTML/JSON) │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 呼び出し
┌───────────────────────────────────▼────────────────────────────────────┐
│  usecase 層 (Application Business Rules)                                │
│  - FillAttendanceUseCase, SubmitWeeklyReportUseCase など               │
│  - 責務: 特定のユースケース（業務シナリオ）の手順調停、トランザクション │
└───────────────────┬───────────────────────────────┬────────────────────┘
                    │ 呼び出し                      │ インターフェース定義
┌───────────────────▼───────────────────────┐ ┌─────▼──────────────────────────────┐
│  domain 層 (Enterprise Business Rules)    │ │  infrastructure 層 (Gateway / DB)    │
│  - DailyAttendance, WeeklyReport,         │ │  - JdbcAttendanceRepository          │
│    SettlementService, OvertimeLevel       │ │  - JdbcWeeklyReportRepository        │
│  - 責務: 純粋な業務ルール・計算・不変条件防衛│ │  - 責務: SQL発行、DB永続化、外部通信  │
│  ★ 外部依存ゼロ（標準Java APIのみ使用）   │ └──────────────────────────────────────┘
└───────────────────────────────────────────┘

鉄則：依存性の方向（Dependency Rule）

依存の矢印は必ず「外側から内側へ」向かいます。内側にある domain 層は、外側の infrastructure（SQL/JDBC）や controller（Servlet/JSP）を絶対に import してはいけません。

Chapter 03

「貧血ドメインモデル」の根絶と自己防衛

本プロジェクトのエンティティには、publicな setter を原則として持たせません。 データ変更は必ず「業務意味のあるメソッド」を経由し、不正な状態が発生した瞬間に例外を投げます。

// domain.attendance.DailyAttendance の自己防衛コード例
public void fillAttendance(LocalTime startTime, LocalTime endTime, int breakMinutes,
                           int abstractId, LeaveType leaveType, String remarks, List<WorkTimeSegment> newSegments) {
    // 1. 月次確定ロックの防衛
    if (this.isLocked) {
        throw new IllegalStateException("月次確定によりロックされているため変更できません。");
    }
    this.startTime = startTime;
    this.endTime = endTime;
    this.breakMinutes = breakMinutes;
    this.segments.clear();
    if (newSegments != null) this.segments.addAll(newSegments);

    // 2. 実労働時間と内訳セグメント（客先＋社内）の整合性を自己検証！
    validateSegmentsIntegrity();
}

private void validateSegmentsIntegrity() {
    int total = calculateTotalWorkMinutes();
    int segmentsTotal = getDirectMinutes() + getIndirectMinutes();
    if (total != segmentsTotal) {
        throw new IllegalArgumentException(
            String.format("実労働時間(%d分)と内訳セグメント合計(%d分)が一致しません。", total, segmentsTotal)
        );
    }
}
💡 これにより得られる効果: メモリ上に「時間が合わない不正な勤怠データ」や「ロックされているのに書き換えられたデータ」が**1ミリ秒たりとも存在できなくなります**。バグは即座に発見され、DBまで汚染されません。
