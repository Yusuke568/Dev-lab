## 1. コアメッセージ：DBや画面は「詳細」にすぎない

本プロジェクト（`webapp2`）は、Spring Boot等のフレームワークを使用せず、純粋なJava標準APIとServlet/JSP環境下で**クリーンアーキテクチャ（Clean Architecture / Hexagonal Architecture）**の原則を徹底して実装しています。

### なぜこの設計思想なのか？
SES勤怠管理システムには、以下のような複雑かつ厳格な業務ルールが存在します：
- 精算幅（140h〜180h）に基づく客先直接時間の控除・割増計算
- 36協定（月45h上限、35h注意アラート）と有給年5日取得義務の進捗監視
- 客先直接時間と社内間接時間（研修・定例会）の分離、および中抜け休憩の自動整合
- 週報（3分割実績）の未入力検知と多層承認ワークフロー（社員提出 → 課長所見 → 所属長最終承認）

これらの業務ルールを Controller や DAO、JSP に直接書いてしまうと、**「少しの改修でどこが壊れるかわからない」「テストのために毎回Tomcatを起動しなければならない」**という開発スピードの激減と品質崩壊（デグレ）に直面します。

そのため、本システムでは**「業務ルール（ビジネスロジック）を純粋なJavaで孤立させ、外部（DBや画面）から守る」**設計を採っています。

## 2. 4層クリーンアーキテクチャの責務と境界線

パッケージ構造は、以下の4層で明確に分離されています。

```
src/main/java/
├── domain/            # 【最重要】純粋な業務ルール・不変条件（外部依存ゼロ）
│   ├── attendance/    # 日次勤怠集約、勤務時間セグメント、テンプレート
│   ├── auth/          # ユーザーセッション、ロール権限
│   ├── compliance/    # 36協定・有給消化コンプライアンス判定
│   ├── contract/      # 契約精算幅・単価計算ロジック
│   └── weeklyreport/  # 週報集約、コメント、多層ステータス
│
├── usecase/           # アプリケーション固有の業務シナリオ（手順の調停）
│   ├── attendance/    # 日次勤怠入力、一括展開ユースケース
│   ├── contract/      # 精算幅計算ユースケース
│   └── weeklyreport/  # 週報提出、レビュー、スキップユースケース
│
├── infrastructure/    # 外部世界との接続（DB、JDBC、SQL）
│   ├── db/            # コネクション管理、トランザクション
│   └── persistence/   # JDBCリポジトリ実装、DAO
│
└── controller/        # Web・UI入出力（Servlet、JSP連携）
    ├── action/        # 画面遷移用Action（GET/POST）
    ├── api/           # Ajax/JSON用Action
    └── FrontController.java
```

### 鉄則：依存性の方向（Dependency Rule）
- **外側から内側へ**: Controller → Usecase → Domain ← Infrastructure
- **`domain` 層の絶対ルール**:
  - `javax.servlet.*`, `java.sql.*` などの外部APIを**絶対に import してはならない**。
  - 純粋な Java 標準API（`java.time.*`, `java.util.*` 等）のみで書くこと。

## 3. 「貧血ドメインモデル」の根絶と自己防衛

従来のJavaBeans（getter/setterだけの受動的な入れ物）を**貧血ドメインモデル（Anemic Domain Model）**と呼びます。これらは誰でも外部から値を改変でき、不正なデータが発生しやすくなります。

本システムでは、**エンティティ自らが不正な状態を拒絶する「自己防衛モデル」**を採用しています。

### 実装例: `DailyAttendance.java` の自己防衛
```java
public void fillAttendance(LocalTime startTime, LocalTime endTime, int breakMinutes,
                           int abstractId, LeaveType leaveType, String remarks, List<WorkTimeSegment> newSegments) {
    // 1. 月次確定ロックの防衛（ロック済なら例外）
    if (this.isLocked) {
        throw new IllegalStateException("月次確定によりロックされているため変更できません。");
    }
    this.startTime = startTime;
    this.endTime = endTime;
    this.breakMinutes = breakMinutes;
    this.segments.clear();
    if (newSegments != null) this.segments.addAll(newSegments);

    // 2. 実労働時間と内訳セグメント（客先＋社内）の整合性を自己検証！
    validateSegmentsIntegrity();
}

private void validateSegmentsIntegrity() {
    int total = calculateTotalWorkMinutes();
    int segmentsTotal = getDirectMinutes() + getIndirectMinutes();
    if (total != segmentsTotal) {
        throw new IllegalArgumentException(
            String.format("実労働時間(%d分)と内訳セグメント合計(%d分)が一致しません。", total, segmentsTotal)
        );
    }
}
```
> **効果**: 不正なデータ（実労働時間と客先・社内内訳が合わないデータ等）は、**メモリ上に1ミリ秒たりとも存在できません**。バグは即座に検知され、データベースを汚染しません。

## 4. テスト容易性（最大の果実）

ドメイン層が外部に依存しないため、**TomcatもMySQLも起動することなく、純粋なJUnitで全業務ルールをミリ秒単位でテストできます**。

```bash
$ mvn test
# 結果: 20テストが約 0.8秒で完了（全件合格）
```
- テストが高速に動くため、開発者は壊れる恐怖を感じることなく、自信を持ってリファクタリングできます。

## 5. 新規機能・改修時の思考ステップ（どこに何を書くか？）

| やりたいこと | 書くべき層 | 実装例 |
|:---|:---|:---|
| 「残業が45hを超えたか判定したい」「精算額を計算したい」 | **`domain/`** | `SettlementService`, `Article36ComplianceService` |
| 「未入力をチェックしてから週報を提出済みに変えたい」 | **`usecase/`** | `SubmitWeeklyReportUseCase` |
| 「MySQLにSELECT文を投げたい」「トランザクションを張りたい」 | **`infrastructure/`** | `JdbcAttendanceRepository`, `TransactionManager` |
| 「リクエストパラメータを受け取り、JSPにフォワードしたい」 | **`controller/`** | `SesAttendanceAction`, `SesAttendanceApiAction` |
